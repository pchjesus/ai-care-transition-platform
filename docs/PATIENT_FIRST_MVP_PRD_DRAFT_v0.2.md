# 환자·보호자 중심 퇴원관리 MVP PRD v0.2

- 2026-10-20 / **ACTIVE DESIGN DRAFT** / 미구현 / 실제 의료진·환자 실증 없음.
- 기존 [기관 워크플로 중심 PRD v0.1](./MVP_PRD_DRAFT_v0.1.md), [서식·의뢰 상세 설계 v0.2](./MVP_WORKFLOW_AND_DATA_CONTRACT_DRAFT_v0.2.md)는 연구·후속 확장용 보존 자료.
- 본 문서의 1차 사용자: **퇴원환자**, 보조 사용자: 동의받은 **보호자**, 계획 발행 주체: 의료진.
- 목표: 가상 퇴원자료에 대해 의료진이 승인한 계획을 환자가 **오늘 해야 할 행동·일정·문의처** 형태로 이해하고 수행할 수 있는지 테스트.
- 첫 환자군 **후보**: 가정으로 복귀하는 고령 복합만성질환자 중 약물·외래·자가관리·돌봄 지원의 복합 안내가 필요한 사례. R05 확인 전 확정 아님.
- **P0는 퇴원 의료계획 안내에 집중**, 공공 서비스·정식 신청·양방향 돌봄은 MVP의 주요 가치 검증 후 P1/P2에 확장.

## 1. JTBD — 성공 장면

가상 환자는 퇴원 전 의료진으로부터 퇴원관리 계획을 안내받는다. 집에 간 뒤 스마트폰 또는 인쇄물에서:
1. **지금 해야 할 일**(승인된 복약/자가관리 안내/준비물)을 찾는다.
2. **언제 어디로 가야 하는지**(외래·검사 일정)를 확인한다.
3. **어떤 상황에 누구에게 연락해야 하는지**(개인별 승인 안내)를 이해한다.
4. 이해하지 못한 점을 확인/질문할 수 있다.
5. 보호자에게 공유하려면 **권한/동의 상태**를 확인한다.

**P0 성공 ≠ 치료 지시의 정당성·재입원 감소·진단 안전성 입증.** 인위적 시나리오에서 정보탐색과 이해·화면작동 검증을 뜻한다.

## 2. 역할 화면

### Patient Home (PRIMARY, 모바일 우선)
- 상단: 가상 환자, 퇴원 일자, 이 계획의 **의료진 승인/갱신 시각**, 변경·미확인 여부.
- **오늘 할 일(첫 화면):** 일정기반·상황기반 카드, 완료/미완료는 '사용자 표시'이지 실제 복약/의료행위 인증이 아님.
- 약 안내: 의료진 승인된 약물명/용법/주의/출처, 임의 변경·스스로 중단 금지 안내.
- 다음 일정: 외래 예약/검사/전화 추적 여부, 일시·장소·연락처/준비사항. 확인되지 않은 예약은 '예약 확정'으로 표시 금지.
- 도움이 필요할 때: 의료진 승인된 개인별 주의증상/연락처/진료 안내; 임의 AI 응급 진단·분류 금지.
- 안내 이해: 짧은 재설명 질문(teach-back 방식 **연구용 시연**)과 문의 항목.
- 접근성: 텍스트 크기, 고대비, 충분한 터치 영역, 쉬운 한국어, 출력 가능한 요약, 일부 시나리오에서 기기 사용 불가 상황 검토.

### Clinician Composer (MINIMUM)
- 완전 가상 환자 정보 선택 또는 입력.
- 관리항목(약, 자가관리, 외래/검사, 주의사항, 문의처) 자동 초안 구성: **첫 버전은 규칙/템플릿 기반**.
- 원천정보·미확인·충돌 필드 표시, 각 항목 수정/삭제/보류.
- 검토·승인·발행 버튼, 시뮬레이션 담당자·시각·버전 기록.
- 최초 계획 발행 이후 변경 시 새 버전 + 변경 내역 표시, 기존 정보 무단 덮어쓰기 금지.
- 환자에게 보이는 공개 스냅샷을 별도로 생성; 미승인 의료진 메모는 절대 포함하지 않음.

### Caregiver Preview (P0 좁게, 보안 구분)
- 최초 MVP의 보호자 화면은 동의 상태가 확인된 **가상 역할 전환 프리뷰**.
- 실제 인증·위임·동의로 주장하지 않음.
- 약물/의료민감정보 전체를 보호자에게 자동 개방하지 않고, 환자가 공유하도록 승인한 가상 범위만 노출.
- 본격적인 보호자 협업·계정·알림은 P1, Firebase 실험 이후에도 보안·법률 검토 필요.

### Community Care Navigator (P1 확장)
- 2026.4 개정 안내로 확인된 신청처/지원계획/중단·종결 정보를 토대로 **가상 서비스** 경로 안내 가능.
- **병원 퇴원 의료계획**과 **지자체 승인 통합지원계획**은 법적 권한·출처/갱신 주체를 분리.
- 정확한 지역 서비스 실시간 가용성·신청/접수/확정은 실연동 전 제공하지 않음.

## 4. 첫 MVP의 기술 계약

- HTML/CSS/Vanilla JavaScript(ES modules) **프런트엔드**, 외부 비밀값/실환자정보 없음.
- Domain 모듈: `care-plan.js`, `publication.js`, `action-schedule.js`, `teachback.js`, `access-scope.js`, `audit.js`.
- Data adapters: `mock-repository.js`, 이후 `firebase-repository.js` (P2).
- 상태: `DRAFT → REVIEW_PENDING → APPROVED → PUBLISHED → REVISED`, 별도 `WITHDRAWN`. APPROVED 이전 공개 금지.
- 환자 할 일의 완료 체크는 '사용자가 앱에서 체크함' 이지 치료완료/복약확인 아님.
- 데이터 객체: syntheticPatient, encounter, sourceRecord, clinicianCarePlan, approvedPlanRevision, publishedAction, visitAppointment, contactGuide, caregiverSharingScope, auditEvent.
- 각 카드 필드: `id, title, category, scheduledAt?, instructions, approvalRef, sourceRef, lastReviewedAt, visibility, status, requiresVerification`.
- 날짜/주기/복약지침 충돌이면 생성·발행 전 검토 요청. 아무 값도 없는 카드에 정확한 처방을 추론·생성하지 않음.
- **Firebase는 다음 단계**; 실제 환자자료를 간단한 프런트엔드나 일반 데모 DB에 저장 금지.

## 5. 최소 수용 테스트

1. 승인 전에는 환자 모드에서 문서/복약·안내 세부 내용이 노출되지 않는다.
2. 환자 A의 일정이 환자 B에게 보이지 않는다(가상 역할 시연 데이터 계약).
3. 의료진이 수정하고 재발행하면 구버전과 신버전 이력이 남고 환자 화면에 버전이 명확하다.
4. 미확인 약 복용량/외래 예약일을 임의로 만들어 내지 않는다.
5. 환자가 퇴원 첫날 '다음 복약 관련 안내·외래일·문의처'를 찾는 태스크에서 정해진 기준으로 성공/오류 판정 가능하다.
6. 복약 체크를 실제 약 복용 증거로 해석하지 않는다.
7. 보호자 시연 모드는 실제 인증이 아니며 가상의 공유 권한이 거부되면 정보를 숨긴다.
8. 일반/긴급 돌봄서비스는 공식 지원·확정 상태를 구분한다(P1 기능).
9. 360px 모바일 화면, 큰 글자, 인쇄와 키보드 접근성, 새로고침/저장/리셋의 회귀 테스트.
10. 공개 배포 전 가상 데이터 외 실명·환자자료·API 비밀정보 0건 검증.

**정량 목표의 초기 제안(검증 전):** 표준 서면 안내 대비 핵심 과업 수행 정확도 및 소요시간·환자 이해도를 비교. 20% 단축·80% 이해도 같은 임의 목표는 조사설계 전 '실제 개선치'로 표현하지 않는다.

## 6. 설계가 필요로 하는 추가 결정

- 첫 환자군: 고령 복합만성질환자의 퇴원 첫날이 최적인지 R05/R13에서 검증.
- 첫 소비자 채널: 병원 QR 안내+휴대폰 브라우저, 종이인쇄, 보호자 공유 중 실제 이해·접근성 높은 방식.
- 병원의 지불 단위: 병원/병동/관리환자 건수/연간 계약 등은 R04/R07 결과로 결정.
- 병원 내부 승인과 공식 지자체 지원계획(통합돌봄)은 **데이터 출처부터 분리**한다.
- UI 가이드: 범용 시각 지침을 참고하지만 건강문해·고령 이용·명확한 정보 위계·행동 안전성을 우선한다.

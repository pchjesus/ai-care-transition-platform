## 1. 제품 원칙과 범위

**핵심 가치:** 병원에서 의료진이 확인한 퇴원계획을 **환자의 다음 행동**으로 이해·실천할 수 있게 하고, 필요한 사람과 공적·민간 서비스를 **안전하게 연결**한다.

- **직접 만들 것:** 승인된 정보의 이해·표시, 쉬운 일정/행동 안내, 고령 사용자 접근성, 상태 및 동의 관리, 연계 과정의 투명한 안내.
- **허가받아 연결할 것:** 병원 EMR/예약·시설 지도·실내 위치 인프라·기관의 실제 접수/의뢰·차량 호출·영양/정신건강 등 전문 서비스.
- **우선하지 않을 것:** 임상 위험 자동 판정·진단·처방 수정·실제 서비스 예약 완료로 오인시키는 목업·외부 전문서비스 직접 운영·무제한 기능 나열.
- **별도 계층:** 의료진 승인된 의료정보 / 환자 자기보고 / 기관 연계 상태 / 비의료 서비스 추천·광고·거래 상태. 이들 사이에 추론으로 상태를 승격시키지 않는다.
- **실데이터 도입 전:** 합성 환자만 사용. `localStorage` 및 공개 체험코드는 인증·기관간 전송·임상 감시 시스템이 아니다.
- **UI:** 현재 승인된 의료진 UX2 및 환자 v1.9.3의 브랜드/사용 흐름 유지. 환자 접근성과 안전을 우선하되 사용자 승인 없이 전면 개편하지 않는다.

## 2. 우선순위 정의 — 중요도와 구현 순서를 분리

- **P0 / 안전·제품 기본:** 기존 기능/데이터 안전 보존, 환자용 정보구조·고령 접근성, 동의/기관 경계 설계. **모든 단계의 필수 조건.**
- **P1 / 다음 개발 사이클 후보:** 병원 층별 지도(정적·경로 예시), 서비스 발견 패널, 음성 안내, 복약 확인·증상 자기보고의 **합성 데이터 버전**.
- **P2 / 파트너·데이터 계약 확인 후:** 환자-보호자 권한 공유, 지역사회 기관 의뢰 상태 연계, EMR·병원별 UI 연동 **실증 설계/모의 어댑터**.
- **P3 / 별도 사업성·인프라 승인 후:** 실내 실시간 위치추적, 실시간 외래 빈자리 예약/확정, 실제 이동·생활서비스 API 및 제휴 수익화, 해외 확장.

**전략 중요도가 높아도 외부 의존성이 크면 실제 구현 단계는 뒤로 간다.** 예: EMR과 기관 연계는 제품의 핵심 차별화 요소이므로 P0에서 **계약·표준과 데이터 구조를 설계**하지만, 실연동은 P2 이상이다.

## 4. 항목별 요구·검토·통과 조건

### FB-01~02. 병원 내부 지도 및 내 위치
- **사용자 가치:** '다음 진료는 언제/어디서?'에서 '어떻게 가야 하나?'까지 연결, 특히 고령자·보행보조기·휠체어 이용자 지원.
- **P1 최소 구현:** **가상 병원** 건물·층별 실내지도, 목적지 검색, 층 이동·연결통로·엘리베이터·장애물 없는 경로(가상 구조), 현재 위치는 **사용자 지정 출발지 또는 QR 체크포인트 시연**으로 표시. 지도/경로의 출처와 시연 표기 필수.
- **P3 실시간 후보:** 실외 GPS와 실내 위치기술을 분리. 정확도·음영·층 오판·방향 표시·센서 보정/권한 거부·배터리·접근성 기준을 현장 협력 후 수립. 내 위치를 자동으로 추측해 정확한 것처럼 표시하지 않는다.
- **통과:** 목적지·층·경로의 일치, 엘리베이터 대체 경로, 위치 미확인 시 수동 시작점, 지도 오류 시 텍스트/접수처 안내. 실제 도면·로고를 허가 없이 공개 저장소에 넣지 않는다.

### FB-03~04. EMR 표준 연동과 병원별 UI 적응
- **사용자 가치:** 새 입력을 늘리지 않고 의료진이 이미 사용하는 업무 안에서 계획 검토·승인·환자 안내를 수행.
- **P0 설계:** 환자/입원건, 의료진 역할, 근거, 약/일정/문서의 승인본, 발행 버전·정정·철회·오류 상태를 **정규화된 내부 데이터 계약**으로 정리. 외부 EMR 데이터는 해당 계약에만 매핑하고 출처·시간·권한을 보존.
- **P2 모의 연동:** 병원별 어댑터와 공식 표준(HL7 FHIR, KR Core, SMART on FHIR 가능 시)을 검토. API 없는 EMR에 무단 접근하거나 화면을 스크래핑해 의료정보를 수집하지 않는다. 의료기관의 공급사·정보보호·연동 승인 및 계약 없이 실제 연동 불가.
- **화면 적응:** 병원이 **사용을 허락한** 색상, 타이포그래피, 메뉴 폭, 컴포넌트 등 디자인 토큰으로 유사한 시각 경험 제공. UI 자체를 무단 복사하거나 로그인·승인·보안의 의미를 흉내 내지 않는다. 승인/발행/환자 식별·안전 알림은 공통 UX·접근성 규칙 고정.
- **통과:** 합성 EMR 어댑터의 데이터 정확성/역할 거부/중복·상충 자료 차단, 상태가 바뀐 승인본의 환자 공개 갱신/철회, UI 변경에 따른 임상 경고·확인 동작 동등성. 현 시점 **실제 EMR 연동 NOT VERIFIED**.

### FB-05. 복약 이행 체크
- **사용자 가치:** 확정된 퇴원 안내를 일회성 열람에서 간단한 일상 확인으로 전환.
- **P1 최소 구현:** 의료진이 승인·발행한 **약 관련 안내가 있을 때만** 개인별 체크 표시. '복용함/복용하지 못함/기억 안 남/해당 없음' 등 비강제 응답; 원래 계획의 처방 용량·시간·복약지시 변경 금지. 시연 시 합성 예시와 승인본 구분.
- **검토:** 실제 복용의 객관적 증명이 아닌 자기보고, 보호자 대리입력 표기, 미응답/지연/계획 개정·철회, 과도한 독촉, 약물별 알림 정확성.
- **통과:** 타인/다른 입원건/미발행/철회된 복약 항목 노출 0; 잘못된 일정 생성 0; 자기보고를 의료진 확인 또는 실제 복용 완료로 바꾸지 않음.

### FB-06. 자가증상 모니터링
- **사용자 가치:** 환자가 몸 상태의 변화를 정리하고 필요한 연락 경로를 빠르게 확인.
- **P1 최소 구현:** 일반적 기분 선택 수준이 아니라, **해당 환자의 유효 발행계획에서 허용한 문항·안내**와 연결된 합성 시연. 입력하지 않음/모르겠음 포함.
- **검토:** AI 자율 진단·임상 위험등급·투약 조절 금지. 응급 주의 문구는 의료진의 사전 확인을 전제. 실제 응답을 누가, 언제, 얼마나 자주 보는지 정하지 않았다면 **모니터링 중/의료진 확인됨**이라고 표시 금지.
- **통과:** 문항/권고/문의처 출처 추적, 계획 버전 불일치 시 차단, 응급 또는 연락이 어려울 때 안전한 기본 안내, 병원 인계가 없는 데모에서 '전송 완료' 금지.

### FB-07. 보호자 정보 공유
- **사용자 가치:** 설명을 반복하기 어려운 환자와 보호자가 **같은 유효 안내**를 참고.
- **P0 권한 모델:** 환자 명시적 동의, 공유 범위(일정만/안내문 등)·기간·열람 로그·취소·기관 변경/입원건 종료, 보호자 본인확인, 연락이 닿지 않는 보호자/무보호자 대안 설계.
- **P2 구현:** 합성 데이터로 대리입력과 단순 열람을 구분; 환자 및 담당자 권한과 재승인 경계 명시. 링크 공유만으로 의료정보 접근 가능하게 하지 않는다.
- **통과:** 동의 없거나 취소·만료 시 열람 불가, 이전 계획·다른 입원건 접근 불가, 보호자 응답을 환자 본인의 자기보고로 위장하지 않음.

### FB-08. 음성 안내
- **사용자 가치:** 작은 글씨, 낮은 문해력, 손 사용 어려움 등을 고려한 정보 접근성.
- **P1 최소 구현:** 핵심 화면·안내문에 **눌러 읽기/일시정지/반복/속도 조절** 추가. 음성 원문은 그 화면의 승인된 텍스트에서 생성하고 합성 시연 여부 일치.
- **검토:** 브라우저/단말 TTS 품질·한국어 발음·의학용어/숫자/시간, 주변 사람에게 들리는 민감정보, 설정 저장과 자동 재생 금지, 저시력·청각 장애 대체 경로.
- **통과:** 승인본 갱신 시 옛 내용 음성 재생 금지, 재생 중 페이지 이동/철회 시 중단, TTS 미지원 시 읽기 가능한 텍스트 유지.

### FB-09. 추가 지원 서비스 찾기
- **사용자 가치:** 많은 기능을 제공해도 발견하지 못하면 사용 가치가 낮아짐.
- **P1 최소 구현:** 환자 홈에 **'나에게 필요한 지원 찾기' 고정·축약 가능한 패널** 배치. 이동지원, 건강/돌봄, 식사, 문의, 지역센터 등을 **'서비스 안내'**로 분류. 의료진이 지정한 필수/확정 안내와 별도.
- **검토:** 방문 가능 지역·자격/요금/신청처/마지막 확인일·서비스 정보 출처·빈 결과. 무분별한 자동 팝업/의료진 안내를 가리는 광고/유료 우선 정렬 피함.
- **통과:** 초기 이용자에게 '오늘 할 일'보다 광고가 우선하지 않으며, 서비스 **안내/신청 시작/기관 접수/승인/이용 완료** 상태가 혼동되지 않음.

### FB-10. 외래 예약
- **사용자 가치:** 재진 일정을 누락하지 않고, 필요하면 병원 공식 예약 경로로 이동.
- **P1 범위:** **이미 확정된 외래 일정 조회**와 병원에서 승인한 문의/예약 변경 연락처·공식 페이지 링크. 디지털 사용이 어려운 경우 전화/대면 경로 우선 제공.
- **P3 조건:** 병원 예약 시스템과 공식 연동하여 실시간 빈자리, 동시 예약 잠금, 확정·취소·변경/실패 회신과 이력 보장. 환자가 임상적 검토 없는 재진 시점을 임의로 바꾸도록 유도하지 않음.
- **통과:** 타인 일정 노출·중복 예약·미확정 일정을 '확정 예약'으로 표시하는 사고 0. 병원 API 부재 시 예약 실행 UI 제공 금지.

### FB-11·17. 고령친화 UI 및 사용성 검증
- **P0 지속:** 기존 색감·승인된 UX 보존, '오늘 할 일/다음 일정/어디로 가나/도움받기' 정보 우선순위 단순화, 쉬운 의료용어와 큰 글씨/높은 대비/버튼 목표 크기, 터치/키보드/스크린리더, 음성·인쇄·보호자 도움 경로.
- **연구:** '다수 피드백'은 개선 우선도를 높이지만 객관적 만족도 수치는 아니다. 고령 사용자·보호자 실제 모집 전에는 가설. 관찰 가능한 **3대 과업**(오늘 할 일, 외래·장소, 도움·문의처) 수행과 시간/도움 요청/실수 기록.
- **통과:** PC/모바일 최소 320/390px, 큰 글씨·움직임 줄이기/모바일 메뉴/본문 스크롤·키보드, 기존 의료진 승인본 상태 설명 회귀, 실제 고령자 시험은 수행 시에만 PASS.

### FB-12~13. 지역사회 기관과 정보 공유·의뢰
- **가장 먼저 탐색할 기관 유형:** ① 보건소·지자체 통합돌봄 창구 ② 의료기관 기반 가정간호/방문간호 관련 조직 ③ 재가복지센터·장기요양기관 ④ 필요시 영양·이동 지원기관. 각 기관의 **업무·대상·법적 자격·자료 수신 가능성**을 먼저 확인한다. 기관명을 적었다고 협력 체결된 것은 아니다.
- **P1 준비:** 기관 유형별 연락/신청 창구, 환자의 서비스 필요·신청 조건·관할 지역, '정보 안내/의뢰 준비' UI를 합성 데이터로 시연. 보건소의 공식 자격 판정·서비스 배정을 대신하지 않는다.
- **P0 데이터 계약:** `referralId`, `patientId`, `encounterId`, `publicationId/version`, 대상 기관·서비스, 환자 동의 범위/기한, 요청자·수신자, 최소 전송 항목, 요청/수신/접수/보완/수락/거절/취소/완료 상태·타임스탬프·오류/재시도 이력. 공유받은 정보에 의료진 미승인 항목 혼입 금지.
- **P2 실연계 전제:** 기관별 접수 담당자·의뢰 수신 채널·책임 소재·보안계약·개인정보 목적/보유기간·철회/정정 처리와 회신 SLA 검증. 실패했으면 성공 표시하지 않고 문의 대체경로 안내.
- **통과:** 중복 의뢰·누락/타기관 전달/철회 후 잔존/수신 오류 등 실패 시나리오, **신청과 접수·수락·서비스 실제 제공을 구별**. 병원/지자체의 확정 지원결과와 본 플랫폼의 준비상태 분리.

### FB-14. 이동지원 — 카카오 T, Uber Health, Grab
- **가치:** 환자 외래·퇴원 귀가 시 교통수단을 찾기 어려운 문제를 줄이고 지역별 외부 서비스를 선택적으로 연결.
- **현재 상태:** 의료진이 공식 목적지 좌표를 확인·발행해야 외부 지도 링크 노출; 택시는 **3단계 이용 준비 설명**이며 실제 호출·예약·결제 아님.
- **P1:** 검증된 목적지/교통수단 정보 안내, 일반 택시/교통약자 이동지원/의료이송 구별, 앱 설치·디지털 사용이 어려운 환자용 전화·보호자 경로.
- **P3:** 한국 카카오 T·Uber Taxi, 영미권 Uber Health, 동남아 Grab 등의 지역별 제공 범위·환자 적합성·API·계약·청구주체를 **후보로 검토**. 우버가 케어브릿지랩에 비용을 지불한다는 주장 **미검증**; 일반 소개만으로 거래 수수료 수익 발생 아님.
- **통과:** 환자 동의 전 위치 자동 전송 금지, 외부 예약이 확인되지 않으면 예약 완료 표시 금지, 취소/변경·실패·가격 주체 명시, 의료적 이송 필요 환자에게 일반 승용차를 적합하다고 추천하지 않음.

### FB-15. 영양·정신건강·독서·사회교류 등 선택형 연계
- **가치:** 퇴원 후 일상 복귀와 삶의 질 지원. 모두를 직접 개발하지 않고 전문 기관/기업이 서비스 제공.
- **P2:** 환자 동의 기반 '생활·회복 지원 서비스' 카테고리의 **안내용 목록** 시연. 영양식은 의료진이 확인한 제한/식이 안내를 임의 변경하지 않고, 정신건강은 인증된 전문서비스·상담/위기 안내와 구분, 독서·사회교류는 환자 선호 중심.
- **P3:** 선정 기준, 서비스 품질/민원/책임/자료 전송 최소화, 실제 계약 가능성 검증 뒤 외부 링크/API 제휴. 불필요한 상품 추천으로 의료정보를 상업화하거나 결제를 강요하지 않음.
- **통과:** 필수 의료안내/선택 지원/광고를 시각·데이터상 명확하게 분리. 서비스를 이용하지 않아도 환자 필수 안내 기능에 불이익 없음.

### FB-16. 수익모델 및 글로벌 확장
- **수익 ① 병원 기본 SaaS/확장형 구독**(현재 단가 탐색 가설), **② 병원 대상 연계 관리 모듈/도입교육**, **③ 법률·계약 검토를 통과한 선택형 비의료 제휴/거래 수익**의 세 축으로 분리.
- 수수료 **지급 주체·요율·실거래 성립·환불·지원비·서비스 품질·법적 환자 소개/알선 제한** 검토 없이는 예상 매출에 포함하지 않는다. 의료/돌봄 서비스의 환자 유인·소개 수수료와 일반 비의료 제휴를 같은 모델로 취급하지 않음.
- 해외: 영미권 Uber Health 및 동남아 Grab 등은 **연계 후보 조사**, 현지 보험/의료제도·개인정보 규정·사업자 등록·계약·현지화 검증 뒤 단계적으로 탐색. 해외 진출/제휴 완료를 주장하지 않음.
- **통과:** 가격 수용도·구매주체·이동 서비스 비용 부담·수익배분 구조를 문서화하고, 조건부 시나리오/실계약을 분리. 2027 사업화 예산 1,000만 원을 매출로 잡지 않음.

## 5. 기술·데이터 안전 공통 계약 (기존 규칙보다 완화 불가)

1. **권위의 원천:** 의료진 승인·발행 스냅샷만 확정 의료안내. 환자 자기보고는 별도 레코드; 외부 기관 수신 결과 역시 별도 증빙. AI 자동 의료지시·발행 금지.
2. **식별·버전:** 동일 환자라도 `patientId`, `encounterId`, `publicationId`, `version`을 구분. 변경·개정·철회·저장 실패 시 지도/약/증상/문서/의뢰가 오래된 계획을 확정으로 노출하지 않음.
3. **접근권한:** 보호자·외부 기관·병원 직원은 각각 별도 권한·동의 범위. 공개 링크/체험코드/`localStorage`는 인증이 아니다.
4. **외부동작:** 지도 URL ≠ 현위치 확인, '이용 준비' ≠ 실제 예약, '신청' ≠ 접수/승인/서비스 제공, '먹었어요' ≠ 객관적 복약 확인.
5. **정보 보호:** 외부 사업자 전송은 목적·최소정보·동의·보관기간·접근 로그·철회·분쟁 해결 검토. 위치/건강정보를 제휴 수익화 기본값으로 수집하지 않음.
6. **미지원 상황:** 오프라인·권한거부·GPS 오차·지도 없음·TTS 불가·예약 API 오류·기관 미응답에 대응하는 대체 안내 제공.
7. **디자인·자산:** 환자 v1.9.3/의료진 UX2 기준선 보존. 병원 UI는 허가받은 구성요소만 설정화하고, 실기관 도면·저작물·환자정보·API 키를 Public GitHub에 저장하지 않음.
8. **검증:** 자동 기능 테스트와 실제 고령자 사용성·병원 실증을 서로 대체하지 않음. 반드시 **PASS / FAIL / NOT RUN / NOT VERIFIED** 표기.

## 6. 단계별 실행 순서 및 시작 가능한 작은 작업

### Gate 0 — 현재 MVP 안전 기준선 유지 (P0, 항상)
- 기존 A1/A2/A3 및 환자 B 연결, 정식 발행/개정/철회, 문서/PDF, 큰 글씨·도움 안내, 저장/복구 회귀 테스트 경계 유지.
- 3대 사용자 과업 평가표와 지원·기관·외부 서비스 **상태 용어 사전** 설계.
- 사용자 피드백은 응답자 수·사용 환경·검증 방식이 확인될 때만 실측 지표로 전환.

### Gate 1 — 독립적으로 보여줄 수 있는 환자 경험 개선 (P1)
순차적인 작은 PR 후보:
1. **환자 홈 정보구조 개선:** '오늘 / 다음 일정·장소 / 도움·지원 찾기'로 더 쉬운 진입, 기존 기능은 유지.
2. **지원 서비스 안내 패널:** 검증 가능한 합성 목록·신청 자격/문의/안내 vs 신청 상태 표시, 광고성 추천은 별도.
3. **병원 지도 v0:** 허가 받은/독자 제작한 **가상 병원 층별 지도**, 수동 시작점·목적지·엘리베이터 동선(실내 GPS 미사용).
4. **음성 안내 PoC:** 현재 유효 발행본 텍스트 읽기·속도·중지, TTS 미지원 대체.
5. **복약·증상 자기보고 PoC:** 유효 발행 스냅샷에 묶인 합성 데이터, 철회/개정·오류·미입력 차단 시나리오.

같은 PR에서 모두 만들지 말고 사용자 가치와 안전을 작은 단위로 검증한다.

### Gate 2 — 외부 계약·보안 아키텍처 확보 (P2)
- 기관 유형별 실제 인터뷰/수신 가능 자료·절차·회신 상태·담당자/업무책임 매핑.
- 합성 EMR 어댑터, 병원별 디자인 토큰(허가 전제), 보호자 역할/동의·만료 시뮬레이션.
- 관련 부서의 실질적인 구매/보안 검토가 없으면 실데이터·실기관 전송 도입 금지.

### Gate 3 — 실시간·제휴 기능 (P3)
- 실시간 실내 측위, 의료기관의 실시간 외래 예약, 실제 지역기관 의뢰·차량 호출/결제·민간서비스 제휴는 **별도 승인/계약/보안 및 실사용 검증** 이후 진행.
- 수수료 계약과 운영비 검증 전에는 매출·고객 유치 달성으로 표현하지 않음.

## 7. 검증 체크포인트·보류 조건

| 검증 대상 | 최소 성공 기준(목표/가설) | 구현 금지 또는 보류 조건 |
|---|---|---|
| 환자 홈/고령 UX | 3대 과업 성공률·도움 요청·오인·완료시간 기록 | 기존 핵심 안내/접근성 회귀 |
| 병원 지도 | 목적지 층/건물·엘리베이터 경로·출발점 미확인 대안 | 도면 출처 불명·환자 위치를 정확한 것처럼 표시 |
| 복약/증상 | 유효 발행본에만 바인딩, 변경/철회·입원건 불일치 차단 | 임의 의료지시·AI 위험 판정·검증되지 않은 담당자 알림 |
| 보호자 공유 | 동의/범위/만료/철회·접근 로그와 차단 시험 | 실인증 없이 개인정보 노출 |
| 기관 연계 | 신청·접수·수락·이용 완료 상태별 기록·재시도/실패 | 수신 기관 권한·보안·책임자 불명 |
| EMR | 합성 데이터 어댑터 매핑/권한 및 오류 시 격리 | 병원/벤더 계약·정보보호 승인 없음 |
| 예약·모빌리티 | 실제 공급자 확정 회신·취소 실패/요금 부담 확인 | 링크만 열고 완료/예약됨 표시 |
| 제휴 수익 | 계약상 지급 주체·요율·법률·환자선택권 검증 | 임의 수수료를 확정 매출로 표시 |

**사용자 테스트 목표와 임상 성과는 분리:** 과업 시간·오인·업무 중복입력·접수율부터 측정한다. 재입원율·합병증 감소를 제품이 입증했다고 주장하지 않는다.

## 8. 다른 문서와의 관계 및 수정 경계

- 현재 제품 구현/배포 상태: [통합 릴리즈 기록](./integration/UX2_PATIENT_V193_RELEASE_20261110.md), [의료진 UX2](../prototypes/hospital-ux2-v07/README.md).
- [R00~R18 환자 중심 검증 로드맵](./RESEARCH_ROADMAP_PATIENT_FIRST_v0.2.md)은 **연구 과제 ID와 당시 근거 기록으로 보존**. 해당 R13(환자 UX), R08(개인정보), R06(기관 연계), R07(수익), R02(EMR) 등에 본 FB ID를 연결해 후속 연구.
- [2026-10 기술 아키텍처 초안](./TECH_ARCHITECTURE_DIRECTION_v0.1.md)은 작성 당시의 후보이며, 현재 코드가 없다는 기술은 최신 구현 상태와 다르다. **Firebase 도입은 확정 기술 결정이 아님**; EMR 연동 및 기관 연계도 현재 미구현.
- 향후 개발 PR마다 관련 **FB ID / 실제 기능 변경 / 기존 기능 보호 / PASS·FAIL·NOT RUN·NOT VERIFIED**를 기록. 기능 구현 없이 문서만 변경했다면 문서 반영으로만 보고.
- **변경 승인 경계:** `main`, 기존 PR, `gh-pages`, 환자 앱의 의료정보 공개 정책·운영용 UI는 별도 사용자 승인 없이 변경하지 않는다.

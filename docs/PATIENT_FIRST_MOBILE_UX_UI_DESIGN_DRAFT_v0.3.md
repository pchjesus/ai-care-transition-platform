## 1. 문제·사용장면·성공 경험

**주요 질문:** "오늘 무엇을 해야 하지? 다음 진료는 언제지? 문제가 생기면 어디에 연락하지?"

## 2. 정보 구조 — 환자 우선

### Bottom Navigation: 3개 고정(제안)
- **오늘**: 개인별 지금 할 일, 승인 최신 여부, 가장 가까운 다음 일정, 다른 안내로 이동.
- **일정**: 시간 순서대로 진료/검사/자가관리계획. 날짜·장소·준비물/연락처, 예약 확인 여부 분명히.
- **도움**: 의료진이 승인한 문의처, 주의상황 안내, 인쇄/보호자/지역 돌봄(추후).
- '내 계획 전체 보기'는 오늘 홈의 명확한 2차 이동경로. 약·자가관리 상세는 독립 숨은 메뉴로 보내지 않고 홈 카드/일정에서 접근.
- 긴급 문의는 UI상의 한 탭 뒤로 숨기지 말고 **홈에서도 도움 경로**를 보여준다.
- P0에 계정 메뉴/소식/커뮤니티/포인트/연속출석/불필요한 공지 및 헬스 데이터 대시보드를 추가하지 않음.

### 의료진 화면(데스크톱 우선, 별도 도메인)
환자 선택 → 원천정보·누락/충돌 검토 → 규칙기반 초안 → 수정 → 승인 → 환자 공개 스냅샷 → 새 계획 발행/철회.
**의료진 디자인을 환자 모바일에 그대로 축소하지 않는다.**

### 보호자
첫 MVP에서는 모의 역할 프리뷰만. 정보 공유를 선택·허용하지 않았다면 환자 정보 미노출. 향후 실제 사용자별 인증·위임·철회 및 접근 로그 설계 필요.

## 3. 홈 화면의 위계와 접힘 구조

1. 상단 한 줄: 임시 서비스명 + **글자 크게**(설정) + "가상 시연" 라벨.
2. 확인 가능한 계획 표시: **계획 버전, 의료진 승인 여부, 마지막 업데이트 시각**. 날짜 미확정일 때 아무 말 없이 현재 계획인 양 표현하지 않음.
3. **"오늘 해야 할 일"**: 처음에는 2~3개 바로 보이게, 나머지 '오늘 할 일 모두 보기'. 임상 중요도는 추정 AI 랭킹으로 임의 변경하지 않고 승인 계획의 우선도/예정시간에 따름.
4. **"가장 가까운 일정"**: 날짜/요일/시각/장소/예약 확정 여부 + 전체 일정으로 이동.
5. **"도움이 필요할 때"**: 증상이나 문의가 발생할 경우 **승인된** 담당기관·연락방법과 확인할 정보를 쉽게 찾음.
6. 하단 상시 3-탭 내비: 오늘/일정/도움. 스크롤 시 가려지는 콘텐츠가 없도록 안전영역 및 하단 패딩.
7. '전체 계획'은 점진적 공개. 핵심 정보 자체를 의도적으로 숨기지 않음.

### 상태 예시(가상 데이터, 의학적 지시 아님)
- 오늘 할 일 ① "보행 보조기 사용 안내 다시 보기" / 세부사항은 가상 의료진이 승인한 텍스트만.
- ② "퇴원 시 받은 약 안내 확인" / 내용 미확인 시 용법·횟수 추정 금지.
- 가까운 일정 "재진 일정 — 날짜 확인 필요": 날짜가 없으면 예약 확정으로 표시 금지.
- 문의처는 실제 연결되지 않은 **가상 연락처**가 있을 경우 화면에 분명히 '모의 정보' 표시.

## 4. 시각 방향 비교: 동일 콘텐츠 기준 2안

| 축 | A. Clear Daylight (권장 시작안) | B. Warm Everyday (비교 후보) |
|---|---|---|
| 소재 해석 | 의료의 신뢰·정보의 정밀도 | 집으로 돌아온 일상·심리적 편안함 |
| 바탕 | 시원하고 거의 흰색의 청백 계열 | 따뜻한 거의 흰색의 중립 계열 |
| 강조 | 깊은 코발트 블루 / 네이비 | 밤색에 가까운 다크 인디고 + 제한된 살구색 |
| 레이아웃 | 텍스트·행동 우선, 선으로 구분 | 간격·가벼운 면으로 관계 구분 |
| 위험 | 지나치게 차가운 병원 업무화면처럼 보일 수 있음 | 감성/크림색에 과도하게 치우치거나 대비가 떨어질 수 있음 |
| 채택 근거 | 모바일 안전정보·링크·액션의 가시성과 상태차를 명확히 보여주기 유리 | 환자 정서적 선호가 검증되면 후속 검토 |

**권장 출발 A안**은 아직 환자 선호도 검증을 받지 않았음. 사용자의 기존 개인 취향을 전국 고령자 선호라고 주장하지 않는다.

### A안 시각 토큰 후보(실제 UI 대비 전체 미검증)
- `--bg: #F7F9FC`
- `--surface: #FFFFFF`
- `--ink: #1E2B42` (본문)
- `--muted-text: #475467` (보조)
- `--action: #1E56BF` (주요 버튼/링크)
- `--soft-action: #EAF1FF` (보조 강조 배경)
- `--pending-ink: #9A5500` (확인 필요 문구; 색+텍스트 병행)
- `--danger-ink: #8B1E2D` (위험/오류; 임상 긴급 분류가 아님)
- `--border: #D7DEE9` (검토·필요 경계)
- 원시 색 대비 사전 계산(흰색 바탕): ink≈14.19:1, muted-text≈7.69:1, action≈6.69:1, pending-ink≈5.72:1. **실제 상태·컴포넌트·비텍스트의 WCAG 통과 판정은 아님**.
- 링크/중요 버튼은 색과 함께 **테두리·굵기·명시적 동사 라벨**을 사용한다.

### 서체·타입
- 후보: 한국어 지원이 명확한 **Pretendard 또는 Noto Sans KR** + `system-ui, "Malgun Gothic", sans-serif` 폴백. 라이선스·실제 한글 글리프·로딩·윈도우/안드로이드 폴백 확인 전 고정하지 않음.
- 한국어 본문 **18px / 줄높이 1.55** 출발점.
- 주요 제목 **26px / 1.30**; 섹션 **22px / 1.4**; 카드 제목 **19–20px / 1.4**.
- 버튼 **18px / 600**, 설명/메타 정보 **15–16px** 이상 제안(중요 상태 텍스트는 본문급).
- 글자 크게 모드: 본문 20–22px부터 테스트, 문서 전체 비례 확대; 200% 확대에서 리플로우·버튼 클리핑 검사.
- 가는 글꼴/이탤릭/작은 영문 레이블을 환자 주요 정보에 쓰지 않는다. 제목은 굵기보다 크기·위치·읽기 위계로 보완.

### 간격·형태·조작
- 360–390px 뷰포트 기준 좌우 패딩 **20px**, 320px에서는 16px까지 재조정.
- 간격 토큰 `8/12/16/24/32px`; 큰 단락 앞은 24–32px, 관련 정보 사이 8–12px.
- 주요 버튼 최소 목표 **48×48 CSS px**(디자인 목표). WCAG 2.2 AA 2.5.8은 24×24 또는 예외이며 48px이 법정 기준 아님.
- 핵심 버튼 높이 52–56px, 오작동 줄이기 위한 넉넉한 버튼 사이 간격 8–12px.
- 카드 반경 12–16px 이하를 출발점으로 하나 만능으로 고정하지 않음. 모든 섹션을 떠 있는 카드로 구성하지 않고 일부는 선/공간으로 정리.
- 항상 보이는 하단 메뉴 3개, 한글 텍스트 라벨 포함, 터치와 스크린리더 포커스 확인.
- 중요한 콘텐츠는 가로 스와이프/캐러셀/숨겨진 롱프레스 없이 접근.

## 5. 의료 안내용 마이크로카피 가이드

| 피할 말/표현 | 권장하는 문구(예) | 조건 |
|---|---|---|
| "퇴원계획 정상 적용" | "의료진이 확인한 안내입니다" | 의료진 승인·발행 확인됨 |
| "투약 완료" 버튼 | "약 안내 확인" | 읽음/체크가 실제 복용 증거가 아님 |
| "F/U OPD" | "다음 외래 진료" | 날짜·부서·장소는 실제 승인정보 |
| "서비스 승인" | "서비스 신청이 접수됐어요" | 접수만 확인됐고 제공 미확정 |
| "고위험/위험도 82" | "확인할 내용이 있어요" | 검증되지 않은 AI 임상점수 사용 금지 |
| "환자 잘못 이해함" | "이 내용을 다시 함께 확인해 볼까요?" | teach-back 결과는 피드백/재교육 목적 |
| "예약 완료" | "진료 날짜를 확인하고 있어요" | 실제 예약 확정 데이터가 없을 때 |
| "빨간색 경고!" | "도움이 필요한 상황입니다 — 승인된 안내를 확인하세요" | 임상 위험 판단·분류 자동화 아님 |

**의학적 주의증상/금기/복약 지시:** 소스에 없는 내용을 친절하다는 이유로 생성하지 않는다. 문자 단순화가 의미를 왜곡하면 원문과 쉬운말을 함께 표시하고 전문가 검토를 받는다.

## 6. 정보 객체·상태의 UI 표현

- Plan: `DRAFT/REVIEW_PENDING/APPROVED/PUBLISHED/REVISED/WITHDRAWN`.
- Medical instruction: `APPROVED/CHECK_REQUIRED/CHANGED/NO_LONGER_VALID`.
- Appointment: `CONFIRMED/PENDING/CHANGED/CANCELLED`.
- Service referral (P1): `RECOMMENDED/REQUESTED/RECEIVED/ACCEPTED/STARTED/ENDED/SUSPENDED`.
- Patient action: `UNREAD/VIEWED/SELF_REPORTED_DONE/SKIPPED`는 **사용자 인터랙션 로그**로만 해석. P0에서는 행동 완료보다 **안내 확인 여부**에 집중; 실제 복약·운동 실천 확인으로 표현 금지.
- Caregiver role: `NOT_AUTHORIZED/AUTHORIZED_PARTIAL/REVOKED` (데모에서는 인증처럼 보이지 않게 명확히).
- 본문에서 `확정된 계획 / 확인 중 / 변경된 안내 / 현재 이용 불가`처럼 **텍스트 상태**를 항상 표시. 색만으로 의미 전달하지 않음.
- 새 계획이 발행되면 변경 내용과 버전을 볼 수 있고, 이전 환자에게 보여준 내용이 조용히 덮어써지지 않도록 수정/발행 이력을 보존.
- 오래된 안내 또는 철회된 계획은 "현재 유효한 안내가 아닙니다"로 표시; 오래된 약 안내를 최신 지시처럼 보여주지 않는다.
- 연결 끊김/저장 실패/재접속 후 **최신 승인 여부를 재확인할 수 없는 경우**, 캐시된 내용을 최신 확정 정보라고 표시하지 않는다.

## 7. 대표 시나리오와 예외 케이스

1. **퇴원 첫날/고령 근골격계 질환:** 오늘 확인할 사항 2개, 다음 외래 일정, 문의처를 10초 내 찾는지 관찰(10초는 초기 테스트 가설).
2. **일정이 아직 확정되지 않음:** 임의 날짜를 만들어내지 않고 날짜 확인 요청/담당 연락 경로 표시.
3. **퇴원계획이 변경됨:** 달라진 내용으로 바로 이동, 승인·갱신일/이전 내용의 상태 확인.
4. **스마트폰 글씨 확대:** 200% 텍스트 확대에도 주요 기능 손실·가로 스크롤 없음.
5. **한 손 조작/손 떨림:** 48px 터치, 버튼 간 간격, 이중탭 방지.
6. **시력이 낮거나 디지털 이용이 어려움:** 인쇄/보호자 안내, 큰 글자 설정, 음성지원은 제품 타당성과 리소스 검토 후 결정.
7. **서비스 신청/접수/확정/중단**: 행정 연계 P1에서는 서로 다른 상태, 담당기관 확인된 것만 발행.
8. **환자가 보호자 공유 거부:** 공유 UI에서 정보를 즉시 차단; 실제 인증은 Firebase 백엔드 이후 별도 구현/보안 테스트.

## 8. 접근성/사용성 검증 계약

### 표준 근거
- WCAG 2.2 AA 타깃: 일반 텍스트 대비 4.5:1, 큰 글씨 3:1, 필수 비텍스트 대비 3:1, 타깃 최소 24px 또는 예외. **프로젝트 자체 48px 목표** 별도.
- 텍스트 200% 확대와 좁은 폭 320 CSS px 리플로우 각각 테스트.
- 사용자 OS 확대, 동작 감소(`prefers-reduced-motion`), 고대비, 키보드 및 Android TalkBack/스크린리더 실제 기기 검증 계획.
- 소형 320/360/390px + 200% 확대, 태블릿/데스크톱 화면 분리.
- 터치 타깃은 UI 요소마다 계산/측정, 페이지별 상태·오류 메시지 포함 대비 검사.
- W3C: https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/
- W3C: https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum
- US Health Literacy Online: https://odphp.health.gov/healthliteracyonline/simplify-navigation-and-search/keep-your-homepage-simple-possible
- https://odphp.health.gov/healthliteracyonline/organize/section-4-5/

### 사용자 시험(미실행)

동일한 정보량의 가상 서면 퇴원안내 vs 신규 UI를 놓고 **정보 탐색 시간, 다음 행동 선택 정확도, 도움/문의처 찾기, 예약 확정/미확정 구분, 큰 글씨·인쇄 만족도**를 비교.
- 환자·보호자 본인 표현으로 다음 행동 설명(teach-back)을 확인.
- 병원의 실제 퇴원환자 모집이나 병원 내 연구는 기관 승인·개인정보·윤리 절차부터 점검.
- 주관적 '깔끔하다' 평가와 **임상 안전/작업 성공**을 분리.
- 개발 전 설계 체크와 실제 브라우저 렌더/작동, 사용자 테스트는 서로 다른 증거 등급. 실행하지 않은 항목은 **NOT RUN**.

### 초기 수용 기준 제안(사용자 승인이 필요한 DRAFT)
- P0 필수 환자 정보 3개(오늘 관리, 다음 진료, 문의처)의 진입 경로가 홈에서 분명하다.
- 중요 상태·승인·변경 정보에 텍스트가 있고, 가짜 확정/완료표시를 하지 않는다.
- 환자 A/B 기록 혼합, 미승인 안내 노출, 의료지시 자동 추정, 보호자 비인가 노출 **0건**.
- 320/360/390px 및 200% 확대에서 심각한 clipping/가로넘침 0건 목표.
- 브라우저 뒤로가기, 재접속, 새로고침, 계획 수정/철회, 날짜가 비어 있는 경우에 안전하게 표시.
- 실제 사용자에서 10초 과제/오류율 등 정량 목표는 표본·과업 난이도를 정한 다음 최종 합격값으로 채택.

## 9. 단계별 후속작업(코드 착수 전)

1. **R13** 환자·보호자 과업 3개 정보구조 및 짧은 마이크로카피를 실제 가상 데이터로 작성.
2. **R05** 고령 근골격계(수술/외래/이동/복약/생활지원) 가상 사례 2개, 정보누락·보호자 공유거부 케이스 1개 작성(임상 정보 전문 검토).
3. **시각 비교 A/B:** 동일 콘텐츠로 Clear Daylight vs Warm Everyday 타이포/팔레트/구획만 비교, 환자 이해도와 미감 평가 분리.
4. **와이어프레임→시연:** 실제 세 메뉴와 의료진 승인 과정, 환자 공개 스냅샷을 소규모 HTML/CSS/Vanilla JS 시연으로 구현하기 전에 사용자 승인.
5. **회귀/안전 계약** 확인 후 코딩. Firebase는 별도 승인된 후속 단계.

**현재는 화면 설계 문서만 생성했고 HTML/JS 프로토타입, 실사용자 테스트, Firebase는 시작하지 않았다.**

# 2026-10-22 — A3 역할·철회 요청 및 A3→B 환자 일치 개선

## 관찰된 문제
- A3에서 약사·담당 의사로 전환하면 전체 ‘승인’이 비활성화돼 개별 역할의 의미를 파악하기 어렵다.
- 통합 홈페이지의 환자용 B 바로가기가 특정 가상 환자(SYN-002)에 하드코딩되어, 다른 환자의 계획을 발행해도 B에서 ‘발행 안내 없음’이 보일 수 있다.
- A3는 다른 역할에도 ‘발행 철회’ 버튼을 표시하지만 실제 handler는 지정 최종 승인자만 실행하도록 차단해 잘못된 기대를 만든다.

## 반영
1. 전문영역 검토(간호사·약사·의사)와 최종 전체 승인/발행(지정 최종 승인자)의 역할을 A3 도움말과 화면에 안내. 실제 계정 권한 부여가 아니라 역할 전환 목업이다.
2. `revocationRequest`는 저장 레코드의 **선택형 최상위 필드**. 기존 schema 2/저장 키·기존 발행본/감사 기록 보존. 작성·검토 담당자가 사유를 입력해 요청하고, 지정 최종 승인자는 반려/철회할 수 있다. 요청만으로 공개 정보를 숨기지 않는다.
3. 허용 역할 외 실행·중복 요청·잘못된 발행 ID·손상된 저장형태를 차단. 발행 철회 자체는 이전 `APPROVER` 권한 제한 그대로. 저장 실패·다른 탭 충돌 시 상태 롤백.
4. GitHub Pages 통합 홈에서 **실제 localStorage 발행 검증을 통과한 가상 환자**를 선택하여 B로 연결. 환자용 B도 현재 선택 환자에 발행본이 없을 때 같은 브라우저의 다른 유효 가상 발행본을 안내. 미발행/철회/타인 데이터를 현재 환자의 발행 정보로 대신 표시하지 않는다.
5. 동적 조회는 기존 `readPatientPublication` 검증 로직을 사용하며 같은 origin/브라우저 컨텍스트에서만 확인할 수 있다. 독립 B v1.3 원본은 수정하지 않는다.

- **PASS:** 이전 저장된 기록에 새 필드가 없어도 계속 읽힘. 철회 요청이 있을 때 기존 발행 해시 및 스냅샷은 변경하지 않음.

## 후속
- 실제 운영 역할 모델은 의료기관 권한 정책·책임·인증 설계가 선행되어야 한다. 추후 작성 의료진 자체 발행이나 역할별 긴급 철회는 **현재 권한을 자동 확장하는 것이 아니라 별도 검토할 정책**이다.
- 실환자 정보, EMR, 실제 승인·기관 전송은 제공하지 않는 합성 과제용 MVP.
